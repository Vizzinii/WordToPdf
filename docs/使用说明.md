## 一、工具用途与解决的问题

本工具用于替代「在 WPS 中打开 Word 文档、手工输出为 PDF、再另行执行图像优化脚本」这一重复性操作，并把后续常见的 PDF 拼接需求一并集成。当前版本提供三类处理能力：选择一个 Word 文档单独转换；选择一个文件夹，对其下所有 Word 文档批量逐个转换；选择多个 PDF，按指定顺序拼接成一份。三类能力共用同一个窗口，通过主界面上方的模式按钮切换。

需要图像优化的原因在于 WPS 的 PDF 导出行为。WPS 在输出 PDF 时，会把 Word 文档内的二值扫描图、少色调色板图统一重新编码为 JPEG。这一处理既显著放大文件体积，也引入有损压缩。以本次实测的 2,145 页检测报告为例，Word 原文件为 55.15 MB，其中 4,101 张插图占 54.23 MB，而 WPS 导出的中间 PDF 达到 465.89 MB；抽样比对显示，导出后的 JPEG 图像与 Word 包内原图平均存在 16.14% 的像素差异。工具以 Word 包内的原始图片字节回填 PDF 图像流，使最终图像的像素内容与 Word 原图一致，同时把文件体积恢复到与 Word 文档相当的量级。

中间那一版 PDF 的作用仅是提供待回填的页面结构与校验基准，不是交付物。工具在优化保真版生成、完整性校验与画质复核均通过后默认删除中间 PDF；如需对照或排查，可在帮助窗口勾选「保留中间 PDF」。「保真」指的是优化过程只改变图像对象在 PDF 内部的编码方式，不涉及重采样、颜色量化或有损压缩；文档的文字、嵌入字体、矢量表格线、页面结构与图像放置位置均不作改动。因此，优化保真版中的图像像素内容与 Word 包内原图一致，不存在以压缩率换取画质的取舍。

V1.2 重点修正了一项影响交付效果的问题。V1.1 的画质复核统一采用「解码像素逐字节比对」，而 JPEG 直通对象在 PDF 中保存的是 Word 原 JPEG 的原始字节，PDF 阅读器与图像库对同一 JPEG 的 IDCT 与色度上采样存在细微舍入差异，会把零损失的对象误判为「不一致」。含较多 JPEG 插图的文档因此长期触发保留兜底，中间 PDF 不会删除。V1.2 改为分层判据：JPEG 直通对象直接比对原始字节，其余对象比对解码像素，判据较此前更为严格，同时消除了上述误报。

## 三、操作步骤

双击 `WordToPdfTool.exe` 打开主窗口。主区域上方是「单个 Word 文件」「整个文件夹（批量）」「合并多个 PDF」三个模式按钮，先选择处理范围，再点击下方主按钮；主按钮文字会随模式变化。主窗口中部显示当前阶段与已用时间，其下为进度条，再下方是历史日志框，处理过程中的每一条信息都会追加到日志中，可向上滚动回看。

单文件模式下，在文件对话框中选择一个 `.docx` 即可开始处理。文件夹模式下，在系统原生文件夹选择器中选定目录后，工具会递归收集该目录及其子文件夹中的全部 `.docx`（自动跳过 `~$` 开头的 Word 临时锁文件），按文件名顺序逐个处理；日志与状态区以「[第几个 / 总数]」显示当前进度，单个文档失败不会中断其余文档，全部结束后汇总成功数、失败数与总体耗时。每个文档的结果都保存在该 Word 文件自身所在目录，不集中到统一输出目录。

每个 Word 依次完成三步。第一步按所选通道（默认 WPS COM）把 Word 另存为中间 PDF，该文件使用临时名称存放；第二步基于既有优化脚本，以 Word 包内原图回填 PDF 图像流，输出 `同名_优化保真版.pdf`；第三步做完整性校验与以 Word 原图为基准的画质复核，通过后自动删除中间 PDF。若同名结果已存在，工具会自动追加 `(2)`、`(3)` 等序号重新命名，不覆盖任何已有文件；勾选「保留中间 PDF」时，中间文件与优化保真版使用相同序号配对命名，例如 `报告(2).pdf` 与 `报告(2)_优化保真版.pdf`。

合并模式下，点击主按钮打开「PDF 合并」窗口。点击「添加 PDF」可一次选择多份文件，列表按加入顺序显示序号、文件名与页数；选中某项后可用「上移」「下移」调整顺序，也可「移除」或「清空」。列表顺序即最终页序，工具严格按该顺序拼接，不做排序或去重。输出文件名可在窗口中修改，默认 `合并结果.pdf`，保存在列表中第一个 PDF 所在目录，同名时同样自动追加序号。点击「开始合并（按当前列表顺序）」后，合并窗口关闭，主窗口的进度条与日志实时显示每个文件的拼接进度与累计页数，结束后给出输出文件名、总页数、体积与耗时。合并过程保留各源 PDF 原有的图像流编码，不做二次重压缩，源文件全部保留不删除。

若在帮助窗口勾选「批量完成后自动合并结果 PDF」，文件夹批量处理结束后，工具会把本次生成的各份最终 PDF 按处理顺序拼接为一份，输出到所选文件夹根目录，默认名为 `批量合并结果.pdf`；单文件模式不触发该动作。未勾选时，仍可随时切换到合并模式，自行选择文件与顺序。

不含可用插图的文档没有可优化的图像，此时工具跳过第二步，直接把导出的 PDF 保留为 `同名.pdf`；这份 PDF 就是最终交付物，不是遗留的中间文件，日志会明确标注。处理期间窗口保持可拖动且不会失去响应；大文档或批量处理通常需要数分钟，请等待日志出现「任务结束」后再关闭窗口。

帮助窗口除载明使用方法与原理外，还提供三个转换方式单选按钮和两个复选框。两个复选框分别为「保留中间 PDF」与「批量完成后自动合并结果 PDF」，默认均不勾选；所选转换方式与两个选项仅在本次运行期间生效，重新启动程序后恢复默认值。

## 四、处理原理

第一步采用 WPS 文字的 COM 自动化接口 `KWps.Application`，以只读方式打开文档并调用 `Document.ExportAsFixedFormat(路径, 17)`。该方法调用的是 WPS 自身的 PDF 导出引擎，与菜单中的「输出为 PDF」一致。实测自动导出与手工导出在 4,101 个图像对象上逐张尺寸与字节数完全相同，两个文件仅相差 219 字节，差异来自生成时间戳与文档标识等元数据。

第二步按像素尺寸分组、以 16×16 灰度指纹逐张匹配 Word 包内的原始图片，再按图像实际颜色数选择编码：JPEG 原图直接回填原始字节；仅含两种颜色的二值图采用每像素 1 位的索引色配合 Flate 无损压缩；三色至 256 色的少色图采用每像素 8 位的索引色。上述分支均为无损重编码，其中二值图由 8 位降至 1 位只是改变同一像素矩阵的容器密度，并未减少信息。文字、字体与版式描述不参与替换。

第三步的完整性校验覆盖页数、文字字符数与图像放置数三项，并额外做画质复核。画质复核采用分层判据：对 `/DCTDecode`（JPEG 直通）对象，直接比对 PDF 内嵌的原始字节与 Word 包内原图字节，字节完全相同即为零损失；对其余无损编码对象，比对解码后的像素矩阵。若某些图像在 Word 包内找不到同尺寸原图（多因 WPS 导出时缩放或裁剪），记为「无法比对」，属于比对基准限制而非画质问题。日志会分别列出「与 Word 原图一致」「其中 JPEG 原始字节直通」「像素不一致」「无法比对」四项数量。

只有同时满足「优化保真版已生成」「完整性校验三项一致」「校验过程正常完成」「画质复核未发现真实像素差异」「未勾选保留中间 PDF」五个条件，工具才删除中间 PDF，并在日志中写明「中间 PDF 仅用于校验，校验通过后已删除」。出现下列任一情况时会保留并改名为 `同名.pdf`：使用者勾选了保留选项；校验过程发生异常；完整性三项不一致；画质复核发现真实像素差异；删除操作本身失败。处理过程失败时另存为 `同名_导出稿.pdf` 便于定位。这样可避免任何无法追溯的情形。

需要特别说明的是，优化脚本日志中的 `img_diff` 表示「WPS 导出的有损 JPEG」与「无损回填后的 Word 原图」之间的差异，在本流程中必然不为零，属于预期现象而非画质下降；判断画质的依据应为工具日志给出的「与 Word 原图一致」复核结果。

PDF 合并使用 PyMuPDF 的页面插入能力，按列表顺序逐个把源文档的全部页面追加到结果文档，写出时启用对象重用与垃圾回收、关闭流重压缩，因此不会改变各页原有图像数据。合并完成后会重新打开结果文件核验总页数是否等于各源文件页数之和，不一致即判定失败并保留源 PDF。

## 五、转换方式选项

帮助窗口下方以单选按钮提供三种导出通道，适用于不同机器环境，选择后即对后续转换生效；其下方的两个复选框分别控制中间 PDF 的保留与批量结果的自动合并。

| 通道 | 适用条件 | 说明与限制 |
| --- | --- | --- |
| WPS COM（默认，推荐） | 本机安装 WPS Office 且 COM 注册正常。 | 无会员要求，与手工导出结果一致，文件大小上限 2 GB。 |
| WPS CLI | 已登录具备 VIP 权限的 WPS 账号，使用金山官方命令行 `wpscli word2pdf`。 | 首次运行需联网下载组件；官方输入上限 200 MB，超限时工具自动回退 WPS COM；图像质量需保持 medium 才能对齐桌面默认导出，选择 high 会使中间 PDF 显著膨胀。 |
| Microsoft Word COM | 本机装有 Microsoft Office，用于未安装 WPS 的机器。 | 版式渲染由 Microsoft Word 负责，与 WPS 排版结果可能存在差异。 |

2 GB 上限的准确数值为 2,147,483,648 字节，仅作用于两个 COM 通道；WPS CLI 的 200 MB 属于官方硬限制，无法在工具内放宽。批量模式下，上限对每一个 Word 文档分别校验，超限文档计入失败并继续处理其余文档。PDF 合并不设单文件体积上限，但超大文件合并时内存占用会随之上升。

## 六、使用限制

当前版本支持单文件、文件夹批量与 PDF 合并三种处理范围，批量会递归包含子文件夹，暂不支持自定义输出目录与排除规则。仅接受 `.docx` 格式作为转换输入，原因是优化阶段需要直接读取 Word 压缩包内的原始图片；旧版 `.doc`、`.wps` 等格式需先另存为 `.docx`。合并模式接受任意来源的 PDF，不要求由本工具生成，但已加密的 PDF 无法合并，工具会明确报错。

工具不会覆盖已有文件，重复处理同一文档会生成带序号的新副本，需自行清理历史输出。V1.1 及更早版本因画质复核误报而留下的中间 PDF 不会被本版自动删除，需人工清理；本版新产生的中间 PDF 均按第四节口径处置。批量处理按文档顺序逐个启动与退出 WPS 自动化实例，总耗时随文档数量线性增长。不含插图的文档只产出一版导出的 PDF，不会产生「优化保真版」。日志框最多保留最近 1,500 行，超出后自动裁剪较早记录，不影响处理结果。

## 八、常见情况说明

出现「自动化接口不可用」或「连接 WPS 失败」时，通常是本机未安装 WPS、WPS 升级后 COM 注册失效，或 WPS 正在以不兼容的权限运行；可先运行命令行脚本的环境自检 `python wps_to_pdf.py --check` 定位，必要时修复或重装 WPS。选择 WPS CLI 通道后若提示 VIP 相关退出码，属官方账号权限限制，改用默认 WPS COM 通道即可。

处理完成后目录中只剩「优化保真版」而看不到普通 PDF，属默认行为；需要对照时请在帮助窗口勾选「保留中间 PDF」。若目录中仍能看到普通 `同名.pdf`，请先确认其生成时间：本版新产生的中间 PDF 会在日志中写明删除结果，较早版本遗留的文件不会被自动清理。无插图文档只生成 `同名.pdf`，属预期结果，日志会标注「导出的 PDF 即为最终交付物」。

批量处理中若个别文档失败，日志与结束汇总会列出失败文件名，其余文档照常完成；失败文档可能留下 `同名_导出稿.pdf` 供排查。处理过程中若观察到 WPS 进程被调起但未见窗口，属预期的隐藏实例行为；工具不会保存或关闭使用者已打开的文档。日志中 `img_diff` 非零的说明见第四节。输出文件名出现 `(2)` 等序号，表明目录中已有同名结果，属不覆盖策略的正常表现。合并时若提示「PDF 已加密」，需先用来源工具去除口令保护。

## 九、附：命令行方式

需要批量处理、切换导出引擎或做维护排障时，可直接运行源码脚本或交付 exe 的自测参数。以下命令中的文件名含中文或空格时应加引号。

```
python wps_to_pdf.py --check
python wps_to_pdf.py "A.docx" --optimize --overwrite
python wps_to_pdf.py "A.docx" "B.docx" -d "D:\output"
python wps_to_pdf.py "A.docx" --engine cli --optimize --overwrite
python optimize_pdf_images.py "A.pdf" "A.docx" -o "B.pdf"
WordToPdfTool.exe --selftest "A.docx" wps
WordToPdfTool.exe --selftest "D:\资料目录" wps
WordToPdfTool.exe --selftest "A.docx" wps keep
WordToPdfTool.exe --selftest "D:\资料目录" wps auto
WordToPdfTool.exe --selftest-merge "D:\out.pdf" "A.pdf" "B.pdf" "C.pdf"
```

其中 `--check` 仅做 COM 实例化与导出能力的环境自检；`--optimize` 串联导出与优化两步；`--engine` 可取 `wps`、`cli`、`word`；`--overwrite` 允许覆盖已有输出。单独运行 `optimize_pdf_images.py` 时，源 PDF 必须是由对应 Word 文档导出的版本，脚本本身不负责 Word 转 PDF。

`--selftest` 供交付验证与故障定位使用，会真实执行一次完整流程并生成输出文件：第一个参数为单个 `.docx` 时处理单文件，为目录时按文件夹模式批量处理；第二个参数为导出引擎；第三个参数传 `keep` 表示保留中间 PDF，传 `auto` 表示批量结束后自动合并结果。`--selftest-merge` 的第一个参数为输出 PDF 路径，其后为两个以上的源 PDF，严格按命令行给出的顺序合并。两种方式的结果都写入系统临时目录下的 `pdf_tool_selftest.log`，包含目标数量、每个文档的页数与体积、画质复核结果、`pdf_removed`、`interim_exists_after`、`final_exists`、合并页数以及总耗时，可用于确认中间 PDF 的处置与合并页序是否符合预期。

## 十、版本范围与后续

V1.0 覆盖单个 Word 文档的两步自动处理、三种导出通道切换、自动避让同名文件、完整性校验与画质复核。V1.1 新增界面放大与字号调整、单文件／文件夹两种处理范围、中间 PDF 在校验通过后默认删除。V1.2 在前两版基础上完成四项工作：修正 JPEG 直通对象的画质复核判据，解决含 JPEG 插图文档中间 PDF 不删除的问题；新增「合并多个 PDF」模式，支持按选择顺序拼接并可上移下移调整；新增可视化进度条与可回看的历史日志框；新增「批量完成后自动合并结果 PDF」选项，使多个 Word 可一步产出一份合并 PDF。

后续可按需扩展记住上次选择的转换通道与保留选项、自定义输出目录、合并时插入书签或分隔页、程序图标等能力。本文档随工具版本同步维护，功能或限制发生变化时应同步更新对应章节。

## 十一、V1.3 版本变更（效率专项）

V1.3 不改变产品行为与交付口径：同一份 Word 产出的「优化保真版」PDF 与 V1.2 **逐像素一致**（200 页 / 600 张插图的回归样本上，页文本与全部图像解码字节的 SHA-256 完全相同，文件体积亦相同）。改动集中在速度、健壮性与可运维性。

### 11.1 逆向还原说明

V1.2 交付的 `WordToPdfTool.exe` 是 PyInstaller 单文件包（Python 3.13）。`pdf_tool.py` 与工作区源码一致，但 `wps_to_pdf.py`、`optimize_pdf_images.py` 此前只以字节码形式存在。V1.3 先从 exe 的 CArchive / PYZ 归档中导出这两个模块的 `.pyc`，逐函数反汇编后重建可读源码，并用「重新编译 + 逐条指令比对」的方式校验：重建版与原字节码在函数集合、参数、局部变量名、常量表与指令序列上等价，仅剩异常表布局与行号的细微差异。两个脚本现已作为正式源码随交付目录提供。

### 11.2 效率改进

| 项目 | 做法 | 效果 |
| --- | --- | --- |
| 图像编码并行化 | 图像对象按 xref 分片，交给进程池编码，主进程只做匹配结果落盘；`--jobs N` 可调，默认按 CPU 自动选择 | 200 页样本 17.0 s → 7.8 s |
| 匹配剪枝 | 新增 `distance_capped`：累计差一旦超过阈值即放弃该候选；`best_match` 一趟同时求出最优候选与距离，不再 `min()` 后再算一次 | 每对象候选比较的成本下降一个数量级 |
| 去 alpha 复合快路径 | 不透明图像直接从 RGB 量化，不再「转 RGBA → 合成白底 → 转 RGB」 | 每张图省两次全图色彩转换与一次混合 |
| Word 插图索引去重 | 同一张 Word 图片在文档内重复出现时只索引一次，并记录全部文件名 | 索引内存与时间随重复率线性下降 |
| 图片取样去 PNG 往返 | `_image_samples` 直接用 MuPDF 的 RGB 采样缓冲，不再「PNG 编码 → PIL 解码 → 转 RGB」 | 校验阶段每对象省两次编解码 |
| 索引复用 | 优化阶段把已建好的 Word 索引返回给画质复核，不再对同一份 docx 建第二遍索引 | 每份文档省一整遍全量图片解码 |
| 批量复用 WPS 实例 | 批量模式整批共用一个隐藏自动化实例，仅在某次导出异常后重建 | 每份文档省 1–3 s 的 COM 启停 |
| 合并写盘 | 合并结果先写 `.part` 再原子改名 | 失败不再留下半成品 |
| 日志控件 | 超出上限时一次性删除头部文本，而不是每追加一行就重设全文 | 去掉 O(n²) 文本重建 |

`optimize_pdf_images.py` 另提供 `--zlib-level N`（1–9，默认 9）。实测把级别从 9 降到 6 可再快约 30%，代价是体积增加约 14%（1.78 MB → 2.03 MB）；要极限速度时可用，默认仍取 9 以保证体积。

### 11.3 健壮性改进

- **原子产出**：优化版与合并结果都先写 `.part`，成功后 `os.replace` 改名。此前直接写最终文件名，崩溃或磁盘写满会留下「名字完整但内容截断」的 PDF。
- **中间 PDF 移出文档目录**：改到 `%TEMP%\WordToPdfTool`。此前建在 Word 同目录，中断即残留几百 MB 的 `.__wps_*.tmp.pdf`，还会被 OneDrive 等同步。
- **可取消**：处理中主按钮变为「点击取消」，逐文档检查取消标志；关窗时若仍在处理会先确认。此前只能等整批跑完或强杀进程。
- **复核异常单独计数**：读取/解码失败不再计入「像素不一致」。此前这类异常会触发「保留中间 PDF」，正是 V1.1 那个症状的另一个入口。
- **COM 错误可读化**：常见 HRESULT 附带中文处置建议；WPS 忙、实例失效等瞬时错误自动重试一次。
- **界面适配小屏**：帮助窗口按屏幕工作区收缩，控件随高度重排。940 × 980 在 1366 × 768 的机器上原本会让底部三个通道单选与两个复选框不可达。
- **落盘日志与台账**：每次运行写 `%APPDATA%\WordToPdfTool\logs\*.log`；批量结束在所选文件夹写「转换记录.csv」。

### 11.4 实测对照

样本：200 页、600 张插图的合成文档（Word 3.00 MB，WPS 风格导出 45.94 MB），本机 4 进程。

| 配置 | 耗时 | 输出体积 | 像素一致性 |
| --- | --- | --- | --- |
| V1.2 优化器（单进程，级别 9） | 22.7 s | 1.78 MB | 基准 |
| V1.3 优化器（`--jobs 1`） | 17.0 s | 1.78 MB | 与基准逐像素相同 |
| V1.3 优化器（`--jobs 4`，默认） | 7.8 s | 1.78 MB | 与基准逐像素相同 |

真实文档的收益随图像数量与 CPU 核数变化：图越多、核越多，并行收益越明显；单图特别大的文档主要受单进程解码速度限制。

### 11.5 体积改进（V1.3.1）

体积专项的结论是：**真正能省的只有「索引色用固定 8 位存储」这一处浪费**，其余方向实测均无收益。

先说清一件事：优化后的产物里，字节几乎只有两类。以真实样本（41 页、55 个图像对象）为例：

| 组成 | 占比 | 能否再压 |
| --- | --- | --- |
| JPEG 直通（Word 原图字节） | 88% | 不能，已到熵下限 |
| 内容流（文字/矢量，Flate） | 9% | 不能，已压缩 |
| 对象字典、xref、文件头 | 3% | 最多省 1.3% |

- **JPEG 直通无空间**：把一张 1200×900 的直通 JPEG 用 q=100 重编码反而膨胀 168.5%，说明直通字节已贴着熵编码下限。实测三份真实 PDF 的 JPEG 段中可剥离元数据（EXIF/ICC/缩略图）为 **0 字节**——Word 内部导出的 JPEG 本来就不带这些段。
- **容器无空间**：换成对象流（`use_objstms=1`）+ `deflate=True` 只省 0.8%–1.3%；`clean=True` 反而增大 1.7%。
- **Predictor 反而变差**：给二值图/索引图加 PNG Up 预测器，实测文件比不加更大（Up +0%、2bpp +24%、4bpp +27%），故不采用。

**真正有效的改动：按调色板规模选择位深。** 原实现无论图里有几种颜色，一律用 8 位/像素存索引。一张 6 色示意图只需要 3 位，存 4 位即可，像素矩阵完全不变：

| 场景 | 改动前 | 改动后 | 变化 |
| --- | --- | --- | --- |
| 40 页扫描件 + 6 色示意图（80 张图） | 1363 KB | 1191 KB | **-12.6%** |
| 41 页真实样本（几乎全是 JPEG 直通） | 1088 KB | 1088 KB | 0%（无索引图可压） |

两组的渲染结果都经逐页像素比对：**0 页存在差异**。

实现要点：索引重打包用「整数移位 + `map(operator.or_)`」，每行按组处理，3 MP 图像约 0.17 s；另有 `_pack_indices` 的参考实现对拍测试（1/2/4 位、多种宽高、不足一字节的行尾填充）全部一致。

**另外开放了一个可选项**：`--bilevel-best` 会对每张二值图同时算 1bpp Flate 与 CCITT G4，取更小者。在扫描文字上 G4 可比 Flate 小约 26%，但它走 `/DeviceGray` + `/Decode [0 1]`，实测部分页面缩放渲染会出现最大 43/255 的通道差（不是数据损失，是查看器的抗锯齿差异）。因此**默认仍是 Flate**，需要极限体积时再显式开启。

### 11.6 真实投标材料实测（V1.3.2）

用 25 份实际投标材料（393.4 MB 的 .docx，合计 1.5 万页）跑完整流程，暴露并修掉三个只会在真实文档上出现的问题。

| 问题 | 现象 | 修法 |
| --- | --- | --- |
| 跨盘移动 | 中间 PDF 在 `%TEMP%`（C:），成品要写 D:，`os.replace` 抛 WinError 17 | 新增 `move_file()`：跨盘时 copy 后同目录原子改名 |
| 实例批量中途崩溃 | 首轮 25 份只成功 13 份，其余报「RPC 服务器不可用 / 远程过程调用失败」 | 新增 `is_instance_dead()` 识别服务端已死，重建实例后**重试该文档**；次轮 25/25 成功 |
| 超 256 色被有损量化 | Word 真彩图强转 256 色索引，约 0.9% 通道被改动（最大差 11 级），与「无损」承诺不符 | ≤256 色走调色板（真正无损）；超过则转真彩无损 Flate（见 11.7），既不降画质也通常更小 |

另加 `sweep_scratch()`：每次任务开始清理上次中断遗留的 `__wps_*.tmp.pdf`。

**实测结果**：1259.7 MB 导出稿 → 418.2 MB 交付，整体 −66.8%；25/25 份页数、字符数、图像对象数全部与导出稿一致，25 份的画质复核「像素不一致」均为 0，中间 PDF 全部删除。（该轮产物 418.2 MB，经 11.7 优化后为 404.3 MB。）

**画质方向需要说清**：交付版与「纯 Word 导出稿」的渲染存在微小差异，因为导出稿里的图片是 Word 二次压缩的有损 JPEG。以 .docx 内嵌原图为基准测逐通道平均绝对偏差：

| 文档 | 纯 Word 导出 | 交付 PDF |
| --- | --- | --- |
| 30_产品相关试验送样检测报告 | 0.7579 | 0.0000 |
| 36_产品质量及运行可靠性 | 1.0756 | 0.0000 |
| 25_技术参数响应表 | 1.7293 | 0.0106 |
| 31_产品研发实力 | 0.9792 | 0.0897 |

即交付版的图片比 Word 自己导出的 PDF **更接近原始素材**，不是画质下降。

### 11.7 体积优先策略（V1.3.3）

目标：**不损失画质的前提下尽可能小**。判据是「不比 Word 原始素材差」，而不是「比上一版小」。

对 25 份真实投标材料（23,626 个图像对象）逐一分析后，只有三处还有空间，且都是无损的：

| 措施 | 说明 | 效果 |
| --- | --- | --- |
| 真彩图无损 Flate | Word 里有 158 张 >256 色的图被导出成有损 JPEG；改用 `/DeviceRGB` + Flate 存原像素 | 14.32 → 7.90 MB，**省 6.42 MB 且画质提升** |
| 索引图按最小位深 | ≤4 色存 2bpp、≤16 色存 4bpp，替代固定 8bpp | 较 8bpp 省约 46 MB |
| 对象流 + deflate | `use_objstms=1, deflate=True` 压缩 PDF 结构，图像字节不动 | 再省 0.7%–1.6% |

**体积优先的具体规则**：某个对象的无损编码若**比 Word 存的原始字节更大**，就保留原件，记为「为省体积保留原 JPEG」。实测全程只有 12 个对象（跨 5 份文档）命中该规则——它们都是 Word 导出时二次压缩过的有损 JPEG，还原成无损要 +27 MB。默认不还原；需要时加 `--lossless-all`。

**最终对比**（旧版指 409.06 MB 的合并单文件）：

| 口径 | 旧版 | 新版 |
| --- | --- | --- |
| 合并成单文件 | 409.06 MB | **400.61 MB（−2.07%）** |
| 25 份分开 | 409.06 MB | **404.30 MB（−1.16%）** |
| 图像净字节（去重后） | 380.95 MB | **374.05 MB（−1.81%）** |

相对 Word 平铺导出（1259.72 MB）整体压缩 67.9%。独立验收：页数 / 字符数 / 图像对象数 25/25 全部一致，画质复核「像素不一致」0 张，中间 PDF 0 份残留。

**已排除的方向**（实测无收益，避免重复投入）：

- PNG 行预测器（`/Predictor` 11/12/15）：511 张索引图测试，0 张变好；
- JPEG 元数据剥离：真实文档的 JPEG 段里可剥离内容为 0 字节；
- `clean=True`：文件反而增大 1.7%；
- `FASTOCTREE` 量化：快 5 倍但改变真彩像素，与无损承诺冲突。

### 11.8 已知未改动项

- 合并仍用 PyMuPDF 的 `insert_pdf` + `garbage=4` 全量重建。超大合并的时间与内存瓶颈在此，换 qpdf 可显著改善，但需引入额外二进制，留待下一版。
- 量化仍取 Pillow 默认的中位切分。实测 `FASTOCTREE` 快约 5 倍，但会改变真彩图的调色板与像素（90 张样本中 39 张不一致），与「逐像素一致」的承诺冲突，故不采用。
- 导出阶段仍逐文档串行：COM 自动化本身不具备安全的并发语义。

### 11.9 原图错配修正与逐页审计（V1.3.4）

**现象**：一份 2,865 页投标材料的交付 PDF 中，第 39、40、46、47、55 页的插图与 Word 原稿不符——第 39 页本应是「计算机软件检测报告」扫描件，成品里却是另一份「应用证明」。而这 5 页的画质复核全部报告「一致」，中间 PDF 照常删除，问题因此对用户完全不可见。

**根因**：`best_match()` 用「同像素尺寸」分桶，再用 16×16 灰度指纹挑最相近的一张回填，门槛为 `DIST_THRESHOLD = 12.0`。第 39 页尺寸 415×587 的桶里有 5 张候选，真正那张与导出图的归一化距离是 8.33，而另一张无关图的距离是 0.00——**匹配器实际在比「哪张图最像已经被导坏的那张」**，于是逐页成对错配（39 页取 A 图、40 页取 B 图，两张图互换了位置），而距离恰好落在门槛之内。

对全量 8,401 个图像对象的距离分布统计，给出了判定依据：

```
0–1 : 8328    合法匹配
1–2 : 0
2–4 : 0       干净隔离带
4–8 : 2
8–12: 3        5 个错配全部落在「合法区间」内
>12 : 55
```

**修正**：

| 项目 | 原逻辑 | 现逻辑 |
| --- | --- | --- |
| 粗指纹门槛 | 12.0 | **1.0**（`DIST_ACCEPT`） |
| 细指纹确认 | 无 | **32×32 指纹，3.0（`DIST_ACCEPT_FINE`）双闸门，两关都过才替换** |
| 不过门槛 | 视为「保留原样」，与「本来就没改」混计 | 单列 `no_original`（无可信同尺寸原图），保留导出图 |
| 画质复核 | 桶内任一张字节命中即算「一致」 | 先定「该是哪张」（同双闸门），再验字节 |
| 页面校验 | 仅页数/字符数/图像放置数 | **新增逐页渲染审计**：导出稿与成品逐页渲染比对，结构性差异（均值 > 9.0 或 4% 以上采样位移 > 40）不删中间稿 |

**验证**（同一份 2,865 页、8,356 张插图的文档，全量而非抽样）：

| 口径 | 数量 |
| --- | --- |
| 逐字节等于 Word 原图 | 7,877 |
| 无损重编码 | 451 |
| 无可信同尺寸原图，保留导出图 | 55 |
| 尺寸桶缺失，保留导出图 | 13 |
| **被新门槛拦下的错配** | **5（p39/40/46/47/55）** |

`7,877 + 451 = 8,328`，与修正前被判为合法的 8,328 个完全相等：合法匹配一个未丢，只精确拦掉了那 5 个。第 39/40/46/47/55 页的图像对象现已与 WPS 干净导出**逐字节一致**。逐页审计 2,865 页无结构性差异；另 51 页存在均值 4.5–6.6 的轻微渲染差异，经抽页确认是回填原图比导出 JPEG 更锐的正常结果（同一张图，非换图）。

**同时修正打包版并行卡死**：`ProcessPoolExecutor` 在 PyInstaller 单文件包中缺 `multiprocessing.freeze_support()`，4 个 worker 全部死锁（实测 935 秒、CPU 占用 0%）。已在 `main()` 首行补齐，重打包后 4 进程并行 193 秒完成。**exe 已按本版源码重新打包**，不再是「只有脚本、需自行构建」的状态。

### 11.10 跳转全量校验与补链（V1.4.0）

**问题**：Word 里的目录项、交叉引用大多是 `HYPERLINK \l "书签"` 域。WPS 导出 PDF 时会把它转成 `/Link` 注解，但实测会漏——域结构异常、书签被删过、标题被改写、模板换代，都会让 PDF 里那段文字看着像链接却点不动，而页数、图像、字符数全部正常，任何既有校验都发现不了。

**新增阶段**：`docx → PDF → 图片回填 → 【跳转校验与补链】→ 合并总 PDF`。位置刻意选在画质与整页审计通过之后、合并之前：此时 PDF 的内容已经确认正确，此后只增删 `/Link` 注解与 `/P`、`/F`、`/Border` 三个键，不动内容流、不动图像流、不动版式，所以不会推翻前面的校验结论；而放在合并之前，是因为每份分册各自补齐后，合并只是顺序拼接，分册内部跳转在合并后仍然成立。

**与「按文字猜」的做法相比，四处改进**：

| 环节 | 朴素做法 | 现做法 |
| --- | --- | --- |
| 判定缺哪条 | 全局保序扫描 | **以规范化文字为键精确配对，同文按序取用**——7 条「（点此返回）」各自对上自己的那处，不会被第一条吞掉全部；再用包含式兜底 |
| 目标页 | 只按大纲标题猜 | 同名命名目标 → **同文字其他链接已指向的页（取众数）** → 书签所在标题 → 显示文字 → 编号前缀 → 近似匹配；都对不上就报告，不猜 |
| 热区 | 整行包围盒 | **字符级坐标**，跨行自动拼接；纵向按 `字号 × 1.5` 展开（实测 WPS 中位比 1.493、中心偏差 0.05 pt），与原生注解对齐 |
| 写注解 | 取 `Annots` 里最后一个 xref | **取插入前后的 xref 差集**，页面原本有别的注解也不会改错对象 |

**实测**：

- 一份 1,371 页、21 个域的文档，首次运行发现并补回第 2 页缺失的「14.1.1 产品质量能力」，热区 `[365.2, 744.2, 464.8, 759.9]` 与相邻 WPS 原生链接 `[111.9, 744.3, 295.7, 759.9]` 的纵向范围一致（偏差 0.1 pt）；重跑新增 0 条，幂等。
- 破坏性回归：人为删除 4 条链接——目录页与正文页的同文条目各一（检验不张冠李戴）、两条「（点此返回）」（检验同文按序配对）。补链后 4 条全部回位，页号与目标页一致，热区完整覆盖文字（最大偏差 3.9 pt，来自段内片段链接的行距差异，点击容错不受影响）。
- 批量 + 自动合并：2 份分册（含一份零插图、79 个域的偏差表）全部通过，合并 80 页，汇总行输出「2 份分册新增链接 0 条」。

**已知边界**（都在报告里显式列出，不静默跳过）：

- 纯扫描页没有文字层，无法定位热区，这类缺失进 `unresolved` 并说明原因；
- 显示文字少于 2 字（如「1」「—」）拒绝定位，避免贴错；
- 外链（`LINK_URI`）无法在本地重建目标，只报告不补；
- 域指向书签在 docx 里不存在（悬空引用，Word 里也点不动）会单独计数，交由原稿修正。
