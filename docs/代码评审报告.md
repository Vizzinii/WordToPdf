## 2. 效率问题（按可改造价值排序）

### E1. 同一份 docx 的插图索引被完整构建两次

**证据**
- `optimize()` 首行就构建索引：打包版 `optimize_pdf_images.py` L421 → `build_word_index`（L240，遍历 zip 内 `/media/` 全部条目，每张图 `PIL.open` + 转 L + 16×16 BILINEAR 缩略图作为指纹）
- `run_pipeline` 之后又调 `quality_check(out, docx, 20)`，其第 3 行再次 `opt.build_word_index(docx)`：`pdf_tool.py:648`

**代价**：实测文档 4,101 张插图，等于每份文档多解压约 54 MB 图片、多解码 4,101 次、多做 4,101 次缩略图。

**改法**：让 `optimize()` 把索引和每对象的匹配结论一并返回，`quality_check` 只做比对不做重建：

```python
# optimize_pdf_images.py
def optimize(pdf, docx, out, use_g4=False, *, return_index=False):
    ...
    results = {}   # xref -> ("jpeg_passthrough"|"g4"|"flate_1bpp"|"png_indexed"|"kept", src_name)
    ...
    return (stats, grouped, results) if return_index else stats
```

```python
# pdf_tool.py::run_pipeline
stats, grouped, per_object = opt.optimize(tmp, docx, out, use_g4=False)
# quality_check 改为接收 grouped，不再调用 build_word_index
```

### E2. 画质复核在重算一遍优化器刚刚算出的结论

`optimize()` 逐对象已经知道：是否命中 Word 原图、命中哪一张、是否走 JPEG 直通、重编码分支。`quality_check`（`pdf_tool.py:633-698`）却重新打开 PDF、重新解码每个对象、重新做指纹近邻搜索、再解码 Word 原图比像素。

**改法**：复核改为「结构级 + 抽样级」两段，成本降到接近 0：
1. 结构级（全量、几乎免费）：`doc.xref_get_key(xref,"Filter")` 与 `per_object[xref]` 对照，确认预期编码已生效、无对象被写坏；
2. 抽样级（少量）：只对随机抽取的 N 个对象做字节/流级校验——JPEG 直通比原始字节（现有逻辑），1bpp/索引色对象把流 `zlib.decompress` 后与由 Word 原图重新派生的 1bpp 位图直接比字节，**不需要 RGB 解码**。

### E3. `_image_samples` 用 PNG 做中间容器

打包版 L537-545（语义等价）：

```python
pix = pymupdf.Pixmap(doc, xref)
png = pix.tobytes("png")            # MuPDF 编码一次
img = Image.open(io.BytesIO(png))   # PIL 解码一次
img = img.convert("RGB")
buf = img.tobytes()
```

每张图 1 次 PNG 编码 + 1 次 PNG 解码，纯开销。`verify_images`（L548-584）对两份 PDF 逐图调用它；`quality_check` 也调用它。

**改法**：直接拿原始采样，避免两次编解码：

```python
pix = pymupdf.Pixmap(doc, xref)
if pix.n - pix.alpha >= 3:
    raw = pix.samples            # RGB(A) 原始字节，零拷贝视图亦可
else:
    pix = pymupdf.Pixmap(pymupdf.csRGB, pix)
    raw = pix.samples
# 需要 PIL 时：Image.frombytes("RGB", (pix.width, pix.height), raw)
```

同理 `quality_check` 里的 `opt.fingerprint(Image.frombytes(...))` 可以直接对 `raw` 做降采样，省掉一次 PIL 往返。

### E4. 完整性校验要「把两份 2,145 页 PDF 的正文各提取一遍」

`verify()`（打包版 L621-648）先 `page_stats(tmp)` 再 `page_stats(out)`；`page_stats`（L516-527）逐页 `get_text()` 与 `get_images()`。对 2,145 页文档就是 4,290 次页面文本提取，只为比较「字符数是否相等」。

**改法**（任选，收益递减）：
- 字符数只对**抽样页**统计（例如 20 页），或用 `sum(len(p.get_text()) for p in sampled)`；
- 或者干脆换成更廉价的等价校验：页面 `Contents` 流字节数之和、`/Font` 资源数量、图像放置数（`get_images` 本来就有）；
- 把抽样页数做成参数（现在硬编码 `20`，`pdf_tool.py:774`）。

### E5. 批量模式每份文档启停一次 WPS 自动化实例

`run_pipeline` 对每个文档 `w2p.start_app(...)` → 导出 → `app.Quit()`（`pdf_tool.py:733-741`），README §六 也写明"按文档顺序逐个启动与退出 WPS 自动化实例"。

**代价**：每份文档多一次 COM 激活/退出（通常 1–3 秒），批量 100 份即 2–5 分钟纯开销；且频繁注册/注销会放大"COM 注册失效"类故障面。

**改法**：批处理级复用同一个隐藏实例：

```python
def run_batch(targets, engine, keep_pdf, sink, progress=None):
    app = w2p.start_app(engine, False) if engine != "cli" else None
    try:
        for ...:
            run_pipeline(docx, engine, sub, keep_pdf, docprog, app=app)
    finally:
        if app is not None:
            try: app.Quit()
            except Exception: pass
```

`run_pipeline` 里若传入 `app` 则跳过启停，只在每次转换后 `doc.Close(WD_DO_NOT_SAVE_CHANGES)`。建议同时加一次「失败重试 1 次」（见 F4）。

### E6. 优化阶段完全串行（可安全并行的部分没有并行）

导出必须串行（COM 单实例），但 `opt.optimize()` 与校验是**纯 CPU + 本地 IO**，与 COM 无关。批量 20 份文档时，若把「已导出待优化」的中间 PDF 交给 2–4 个进程并行优化，批次总耗时可由「导出+优化」之和降到接近「导出」之和。

**改法**：`concurrent.futures.ProcessPoolExecutor(max_workers=N)` 跑 `opt.optimize`，worker 数默认 `min(4, cpu_count-1)`，GUI 里给个 1–4 的选项。注意：现在 `run_batch` 通过 `opt.emit = emit` **猴补丁改模块全局**（`pdf_tool.py:877`），多进程/多线程下会串消息——先改成显式传入 `sink` 再并行。

### E7. 合并路径是「全量重建」，也是大文件的内存峰值点

`merge_pdfs`（`pdf_tool.py:913-966`）：逐个 `insert_pdf` 到内存文档，最后一次 `result.save(out_path, garbage=4, clean=False, deflate=False)`。

- `garbage=4` 会对全部对象做重编号与去重扫描，3,456 页 / 100+ MB 级别时这一步通常是耗时与内存主因；
- 整份结果常驻内存，README 也承认"超大文件合并时内存占用会上升"。

**改法**（按推荐度）：
1. 引入 **qpdf**（单文件 ~2 MB，随 exe 一起分发）：
   `qpdf --empty --pages a.pdf b.pdf c.pdf -- "out.pdf"` —— 逐页搬运、不解析图像流、内存常数级，速度通常比 PyMuPDF 全量重建快一个量级；
2. 或保留 PyMuPDF 但降到 `garbage=1, deflate=False, clean=False`，并改用 `writer = pymupdf.open(); writer.insert_pdf(src, links=True, annots=True)` + `writer.ez_save(out)`；
3. 无论如何加进度（现在只在文件粒度报进度，单个 2,145 页文件内部无进度）。

### E8. `ComputeStatistics(WD_STATISTIC_PAGES)` 只为打印一句提示

打包版 `export_doc`（L366-433）在导出后统计页数，仅用于「WPS 统计页数 %d，实际 PDF 为 %d 页」这类提示。对 2,145 页文档这是一次完整排版统计。

**改法**：删掉该调用，直接用 `pymupdf.open(pdf).page_count`（`pdf_info` 本来就有），页数不一致时再告警。

### E9. 少色图分支的 `quantize()` 是逐像素开销

`encode_stream`（L363-416）对非二值图走 `img.quantize()`（中位切分）→ `getpalette()` → 取索引字节。对 4,101 张图，这是优化阶段的主要 CPU。

**改法**：
- 若 Word 原图本身就是 PNG-8/调色板格式（`Image.mode == "P"`），**直接复用其调色板与索引字节**，跳过 `quantize()`；
- 只有确属真彩色但颜色数 ≤256 的图才 `quantize(colors=256, method=Image.Quantize.FASTOCTREE)`（比默认 MEDIANCUT 快很多，且此处颜色数少，质量差异可忽略）；
- 二值判定已有 `_pure_bw_palette`（L290）先用它短路，避免对大图做无谓量化。

### E10. GUI 日志与重绘的隐性二次方

- `append_log_lines`（`pdf_tool.py:1215-1233`）：超过 1,500 行后**每追加一行**都用 `WM_SETTEXT` 重建整个文本（约 100 KB），属于 O(n²) 文本重建；
- `WM_TIMER`（L1417-1455）每 200 ms 排空队列后有变化就整窗 `InvalidateRect`，`draw_main` 走 `CreateCompatibleBitmap` 全窗双缓冲重绘；
- `sink()` 每条消息入队两次（`"log"` 与 `"status"`，L1030-1032），GUI 侧两条都处理。

**改法**：日志区独立 `InvalidateRect(HWND_LOG_...)`；裁剪时用 `EM_SETSEL` 一次性删除头部而不是重建全文；状态行与日志行复用同一条消息；进度条单独重绘。

### E11. 打包形态本身是启动成本

`--onefile` 每次启动解压 154 MB（实测），其中 `pymupdf` 解压后 93 MB、`numpy` 6.1 MB、`numpy.libs` 20.2 MB、`PIL` 12.9 MB。团队内分发建议 **`--onedir`**（一个文件夹，双击同目录 exe）：启动接近即时、无 `%TEMP%` 抖动、故障时不会留下 154 MB 的 `_MEI*` 残骸（本机已残留一个）。

## 3. 功能与健壮性

### F1（P0）输出非原子：崩溃即留下「看起来正常」的坏 PDF

`opt.optimize(tmp, docx, out, ...)` 直接把成品写到最终名（`pdf_tool.py:749`），`merge_pdfs` 直接 `result.save(out_path)`（L948）。若在 save 过程中崩溃、磁盘满、或被用户关窗（daemon 线程被强杀），磁盘上会留下**截断但名字完整**的 `xxx_优化保真版.pdf` / `合并结果.pdf`，同事打开才发现坏了；而「不覆盖已有文件」的设计让下次运行还会再生成 `(2)`，问题被掩盖。

**改法**：一律写 `out + ".part"`，成功后 `os.replace(part, out)`；失败 `os.remove(part)`。三处都要改：optimize 输出、merge 输出、无插图分支的 `os.replace(tmp, plain)`（L755）保持原样即可。

### F2（P0）没有取消，关窗即中断，临时文件落在用户文档目录

- 无「取消」按钮，批量 50 份只能整批等（README §三 还叮嘱"请等待任务结束"）；
- `WM_DESTROY`（L1525-1528）直接 `PostQuitMessage`，worker 是 `daemon=True` 线程（L1381-1383），进程退出时被强杀；
- 中间文件建在**源文档同目录**：`unique_paths`（L616-630）→ `"%s.__wps_%s__.tmp.pdf"`。中断即残留，OneDrive/网络盘还会同步这份几百 MB 的临时文件。

**改法**：
1. 加 `threading.Event` 取消标志，在「文档之间」「阶段之间」「每 N 张图」检查；主按钮在忙时变成「取消」；
2. `WM_CLOSE` 时若 `STATE["busy"]`：弹确认「正在处理，确定中止？将清理临时文件」；
3. 中间 PDF 写到 `%TEMP%`（或其子目录）而非源目录；仅最终成品写回源目录（同盘 rename 才是原子的，跨盘需要 copy+replace）。

### F3（P0）帮助窗口在 1366×768 上不可用

`HELP_W, HELP_H = 940, 980`（L290），控件按绝对坐标排到 y=962：单选按钮 `706 + i*44`、复选框 844 / 886（L1245-1272）。`MAX_H` 用 `max(0, (sh - h)//2)` 定位（L1178），在 768 高的屏上窗口顶端贴 0、底端 980 超出 212 px，**且帮助窗口不可滚动**（只有 HELP_TEXT 的 EDIT 有滚动条）→ 那台机器上换不了转换通道、勾不了「保留中间 PDF」「自动合并」。

**改法**：`h = min(HELP_H, work_area_height - 24)`，把 `_HELP_TEXT` 的 EDIT 高度改为 `h - 200`，底部选项区改为相对 `h` 定位；或把选项搬进主窗口。

### F4 失败不重试，COM 错误不翻译

`run_batch`（L892-899）一次异常即记失败。而 WPS COM 的失败常常是瞬时的（实例忙、弹窗、文档被占用）。错误信息目前是 `TYPE：str(exc)`，用户看到 `com_error 0x800A…` 无从下手（README §八 只给了 `--check`）。

**改法**：对 `export_doc` 失败重试 1 次（间隔 1.5 s，重试前 `Quit` 旧实例）；建立 HRESULT → 人话映射表（未安装 WPS / 以管理员运行 / 文档被占用 / 文档加密 / 路径过长）。

### F5 输出目录写权限不预检

`start_merge_job`（L1387-1407）用第一个 PDF 的目录作输出目录，没有 `os.access` 检查；只读网络盘或 U 盘上要等全部拼接完才报错。批量模式同样：跑到第 30 份才发现某个子目录只读。

**改法**：开工前对每个目标目录做一次 `tempfile.NamedTemporaryFile(dir=...)` 探测，失败的目录提前剔除并明确报错。

### F6 DPI 与屏幕适配

`SetProcessDpiAwareness(2)`（L62-68，per-monitor v2）但**所有坐标、字号都是硬编码像素**（L289-316 的布局常量、`make_font` 的 `-size`）。本机实测主屏物理 2560×1440、按 150% 缩放（未感知 DPI 的进程报告为 1707×960）：该 exe 按物理像素绘制，980 px 窗口只占宽度 38%，14 px 字号在 150% 下偏小；换到 4K/200% 更明显。

**改法**：启动时取 `GetDpiForWindow`/`GetDpiForSystem`，定义 `def S(v): return int(v * dpi / 96)`，布局常量与 `make_font` 全部过一遍；再叠加 F3 的 work-area 钳制。

### F7 窗口形态

`WS_POPUP | WS_VISIBLE | WS_CLIPCHILDREN`（L1782-1785）且无 `WS_EX_APPWINDOW` → **任务栏没有按钮**、不可最小化、不可调整大小。对一个「大文档要跑几分钟」的工具，用户只能 Alt+Tab 找它。

**改法**：`WS_EX_APPWINDOW`；给 `WS_THICKFRAME` 或至少允许高度拖动（日志区随窗口拉伸）。

### F8 不支持拖放

最自然的入口是把 `.docx` 或文件夹拖到窗口上，现在必须点按钮走两次系统对话框。加 `DragAcceptFiles` + `WM_DROPFILES` 约 30 行。

### F9 设置不持久化

`ENGINE / MODE / KEEP_PDF / AUTO_MERGE` 是模块全局（L341-344），README §三 也写明"重新启动后恢复默认值"，§十 把它列为后续。写 `%APPDATA%\WordToPdfTool\settings.json` 即可，顺手可存「上次选中的目录」。

### F10 抽样判据固定，且有残留误报源

- 抽样页固定步长：`step = max(1, n // sample_pages)`，`pages = range(0, n, step)[:20]`（L653-656）——同一份文档每次抽同样的页，坏页会被系统性漏检；
- `quality_check` 的兜底 `except Exception: pixel_diff += 1`（L692-693）：**解码/读取异常被计成"真实像素差异"**，从而触发保留中间 PDF——这正是 V1.2 想消灭的症状，只是换了个入口（例如某张图 `_image_samples` 抛 TypeError 就会命中）。

**改法**：异常单独计 `check_error` 并在日志与结论中区分；抽样改用 `random.Random(seed).sample` 且把抽到的页码写进日志；抽样页数与开关做成参数。

### F11 无落盘日志、无批量报表

日志只活在 EDIT 控件里（上限 1,500 行，L1224）。团队批量跑 100 份后，要回答「第 37 份为什么失败」「哪份复核不一致」只能靠翻屏。

**改法**：`%APPDATA%\WordToPdfTool\logs\YYYYMMDD-HHMMSS.log` 全量落盘；批量结束额外写一份 CSV（文件名、页数、导出体积、成品体积、一致/不一致/无法比对、耗时、结果），交给他们做验收台账。

### F12 合并功能的缺口

- 不支持书签/大纲合并（`insert_pdf` 不带 TOC 偏移处理），几百页合并后目录全丢；
- 只能上移/下移，不能拖动、不能按文件名/页数排序；
- 无分隔页、无「每份之间插空白页」；
- 输出名把扩展名归一化的逻辑有坑：`unique_output`（L602-613）对 `a.txt` 会拼成 `a.txt.pdf`；
- `choose_pdfs` 用 65,536 字符缓冲（L1109-1119），多选数百个长路径文件会静默截断且不报错。

### F13 「不覆盖」的并发缺口

`unique_paths`（L616-630）先算名字后写盘，中间没有占位；两个窗口同时处理同一文档会得到同一个名字，第二个直接覆盖第一个的成品。建议用 `open(path, "x")` 先占位（`O_EXCL`）再写入。

### F14 批量排序口径与 README 不符

`collect_docx`（L849-857）返回 `sorted(full_paths)`，即**按完整路径**排序：同一子目录内的文件按名有序，但整体上是「子目录成组」，不是全局文件名顺序。README §三 写的是"按文件名顺序逐个处理"。

### F15 无「只导出/不优化」的降级通道

遇到优化阶段内存不足（打包版 `main` 已有 `MemoryError` 分支），文档直接失败。建议降级为「导出稿即为成品 + 告警」（`_导出稿.pdf` 已经存在这套命名）。

### F16 猴补丁式日志注入

`opt.emit = emit`（L877）与 `w2p` 各自的 `emit` 分离：GUI 只接了 `opt` 的，`w2p` 的导出消息（含 WPS 版本、接口名）在 windowed 模式下写进 `devnull`（L42-45），日志里看不到。改成显式传入 `sink`/`logger` 对象。

## 6. 已经做对、不要动的地方

评审中这些设计是有效的，改动时应保留：

1. **分层画质判据**（JPEG 直通比原始字节、其余比解码像素）——正确识别了"PIL 与 MuPDF 的 IDCT 舍入差"这一真问题；
2. **"无法比对"与"像素不一致"分开计数**，且前者不阻断删除——判据克制、口径清晰；
3. **中间 PDF 的删除有明确五条件**，日志逐条写明原因（可追溯性做得比多数内部工具好）；
4. **绝不覆盖、自动 `(2)` 序号**——对交付场景是正确取舍（只是需要 F13 补一个原子占位）；
5. **失败另存 `_导出稿.pdf`**，保留现场；
6. **`--selftest` / `--selftest-merge`** 自带端到端自检并写结构化日志（`pdf_tool.py:1678-1742`）——建议扩成正式验收脚本；
7. **无第三方 GUI 框架**，纯 `ctypes` + Win32，双击即用、无安装依赖，这个约束值得保持。

## 8. 附录：量化与回归脚本

评审中可在真机上复现的三条命令（无需改动交付物）：

```powershell
# 1) 端到端回归（含中间 PDF 处置与合并页序）
WordToPdfTool.exe --selftest "D:\测试\文档一.docx" wps
WordToPdfTool.exe --selftest "D:\测试" wps auto
WordToPdfTool.exe --selftest-merge "%TEMP%\m.pdf" a.pdf b.pdf c.pdf

# 2) 启动成本（每次启动都会解压一遍）
Measure-Command { $p = Start-Process WordToPdfTool.exe -PassThru; Start-Sleep 3; $p.Kill() }
Get-ChildItem $env:TEMP -Filter '_MEI*' -Directory | % { "{0} {1:N1} MB" -f $_.Name, ((Get-ChildItem $_.FullName -Recurse -File | Measure-Object Length -Sum).Sum/1MB) }

# 3) 热点定位（把 pipeline 各阶段耗时打出来，替代"感觉慢"的猜测）
python -c "import cProfile,pstats,sys; sys.argv=['pdf_tool.py','--selftest','样本.docx','wps']; cProfile.run('import pdf_tool; pdf_tool.main()','prof.out'); pstats.Stats('prof.out').sort_stats('tottime').print_stats(20)"
```

> 第 3 条需要 `wps_to_pdf.py` / `optimize_pdf_images.py`（见 B1）。补齐后跑一次，就能把 E4（全文提取）、E9（quantize）、E3（PNG 往返）的实际占比钉死，再决定第二批的投入顺序。
