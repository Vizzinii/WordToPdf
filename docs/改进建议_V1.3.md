## 3. 效率：一份 41 页文档到底花在哪

同一份文档、同一台机器，逐阶段计时（秒）：

| 阶段 | 耗时 | 占比 | 说明 |
| --- | --- | --- | --- |
| `start_app`（WPS COM 实例化） | 1.06 | 10% | 每份文档一次 |
| `export_doc`（导出 PDF） | 2.72 | 25% | 真实工作，无法省 |
| `build_word_index`（第 1 次） | 0.26 | 2% | 55 张图 |
| `optimize`（回填） | 2.22 | 20% | 真实工作 |
| `opt.verify`（完整性 + 图像 + 渲染） | **2.48** | **22%** | 图像与渲染部分**结果没人用** |
| `quality_check`（画质复核） | **1.86** | **17%** | 重算一遍 + PNG 往返 + 重建索引 |
| `build_word_index`（第 2 次，`quality_check` 内） | 0.17 | 2% | 纯重复 |
| 合计 | **11.10** | | 校验链路占 **41%** |

### E1 画质复核在重算优化器的结论，而且判据更差

`optimize()` 逐对象已经知道「命中哪张 Word 原图、走了哪个编码分支」。`quality_check()`（`pdf_tool.py:633-698`）却重新打开 PDF、重新解码每个对象、重做指纹近邻搜索、再解码 Word 原图比像素。**同一件事做两遍，第二遍更贵也更不准**（见 C1）。

### E3 `_image_samples` 的 PNG 往返是纯开销（实测 36×）

同一批 19 个对象、39.2 MB 像素：

```
opt._image_samples（现实现：Pixmap→PNG→PIL→RGB）   0.43 s
直接取 Pixmap.samples                             0.012 s     返回值逐字节相同（mismatches: 0）
```

4101 张图的文档，这一步换算下来约 **90 s → 2.5 s**。

### E1b Word 插图索引重复构建

真实 selftest 日志里，4101 图文档「Word 插图索引完成：4101 张，用时 14.6 秒」。`quality_check` 里再建一次，**这 14.6 秒不出现在任何日志里**。修法：`optimize()` 把 `grouped` 一并返回，复核只接收。

### E4 `opt.verify` 里有两段永远没人读的工作

`run_pipeline` 只用 `integrity` 的 `pages/chars/placements`（`pdf_tool.py:774-779`）。而 `opt.verify` 还会：

- 抽样页逐图做**解码像素比对** → 恒报 `img_diff`（README §四 自己解释了为什么必然非零）；
- 抽样页做**整页渲染诊断**（`verify_render`）→ 结果无人使用。

实测这两段占 `verify` 的 2.43/2.48 s。删掉后剩下的 `page_stats`（41 页 ×2 次 `get_text`）只要 0.05 s；2145 页文档约 2.6 s，也可只统计抽样页。

### E5 批次每份文档起停一次 WPS

`start_app` 实测 1.06 s（冷）/1.49 s（含 WPS 启动），`Quit` 0.01 s。25 份批量 = 约 30 s 纯开销。批处理级复用一个隐藏实例即可：

```python
def run_batch(targets, engine, keep_pdf, sink, progress=None):
    app = w2p.start_app(engine, False) if engine != "cli" else None
    try:
        for i, docx in enumerate(targets, 1):
            run_pipeline(docx, engine, sub, keep_pdf, docprog, app=app)
    finally:
        if app is not None:
            try: app.Quit()
            except Exception: pass
```

`run_pipeline` 里传了 `app` 就跳过 `start_app/Quit`，每份结束时 `doc.Close(WD_DO_NOT_SAVE_CHANGES)`。

### E9 优化阶段的热点分布（cProfile，样本）

| 函数 | tottime | 占 optimize |
| --- | --- | --- |
| `ImagingCore.quantize` | 0.676 s | 28% |
| `ImagingCore.convert` | 0.371 s | 15% |
| `builtins.max` | 0.254 s（**711 次调用**） | 11% |
| `ImagingDecoder.decode` | 0.250 s | 10% |
| `PIL._imaging.alpha_composite` | 0.184 s | 8% |
| `zlib.compress` | 0.036 s | 1.5% |

两个可落地的小改法：

1. **`max` 711 次**说明像素级循环里在反复调 Python 内置函数。二值分支已有 `bytes.translate`，把 `luma`/阈值那段也改成 `bytes.translate` + `int.from_bytes` 位打包，或直接用 `img.point(...).convert("1")`，可把这 0.25 s 与 0.31 s 的 `flate_bilevel` 一起压掉。
2. **`quantize` 前的短路**：Word 原图本身是 `mode == "P"`（PNG-8）时，直接复用其调色板与索引字节，跳过 `quantize()`；只有真彩色但 ≤256 色的图才量化，且用 `Image.Quantize.FASTOCTREE`（比默认 MEDIANCUT 快数倍，颜色少时差异可忽略）。

## 4. 正确性：三个可复现缺陷

### C1（P0）透明图像被误判为画质下降，中间 PDF 被保留

**现象**：一个含 RGBA PNG 的文档，`quality_check` 报 `(checked=12, same=9, diff=3, nocand=0, byte=3)` → `pdf_tool.run_pipeline` 判定「画质复核存在 3 张真实像素差异」→ **中间 PDF 被改名为 `同名.pdf` 保留**。而页面实际渲染是正确的（透明区域正常透出白底，实测页角渲染为 `(255,255,255)`）。

**根因**：`_image_samples` 对「`/Indexed` + `/SMask`」对象取到的是 **4 通道** Pixmap（`len(samples)=1,080,000`，而 RGB 只有 `810,000`），随后 `convert("RGB")` **直接丢弃 alpha**；Word 侧 `original.convert("RGB")` 同样丢 alpha。于是两边都在"丢 alpha"，但 MuPDF 对完全透明像素给出的颜色是**不确定值**（实测该像素返回 `(0,255,255)`，而 Word 原图处是透明黑）。逐字节比对必然不等 → 误判。

复现链路（可写进回归用例）：

```
docx: 3 页，含 RGB-JPEG / RGBA-PNG / 1bpp-PNG / P-PNG
PDF 对象：5 个，其中 1 个带 SMask
quality_check → diff=3   ← 误判
SMask 流实测 alpha 取值 {0,128,255}，说明透明度本身写对了；页面渲染角点 = 白
```

真实 25 份 selftest 日志里，第 3、6、10 份文档同样出现「1～3 张真实像素差异」并因此保留了中间 PDF——按本节机制，这些极可能都是同一类误判，不是真的画质下降。

**修法（推荐）**：不要再比解码像素。`encode_stream` 是**确定性**的——同一张 Word 原图 + 同一组参数必然产出同一条流。实测：把每个对象用 Word 原图重算编码流，与本 PDF 的 `xref_stream_raw()` 逐字节比，**60/60 与 12/12 对象完全一致**。所以：

- 复核判据改为「重算流 == 本 PDF 原始流」，字节相等即**构造性证明零损失**，与 JPEG IDCT、SMask、透明像素取值全部无关；
- 重算不匹配时（例如 WPS 导出时缩放/裁剪导致 `kept`），再回落到解码像素比对，且透明图**两侧都按白底合成**；
- 抓不到原图的仍记「无法比对」，不阻断删除。

`hotfix/v13_fidelity.py` 就是这个实现，实测：同一份 alpha 样本 `diff=3 → 0`，耗时 `0.28 s → 0.09 s`。

### C2（P0）解码异常被记成「真实像素差异」

`quality_check` 的兜底 `except Exception: pixel_diff += 1`（`pdf_tool.py:692-693`）。任何解码/读取异常都会直接触发"保留中间 PDF"，把"工具自己出错"显示成"画质有问题"。修法：单独计 `check_error`，并在日志与结论里区分；`check_error > 0` 时保留中间 PDF 是合理策略，但**理由要写对**。

### C3（P1）`img_diff` 这个名字本身在误导

`opt.verify` 与 README §四 都承认 `img_diff` 表示「WPS 有损 JPEG ↔ 无损回填」的差，必然非零。它以 `img_diff` 出现在报告与 `--selftest` 日志里（实测 41 页样本 `img_checked=37, img_diff=37`，100% 命中），任何人第一次看到都会当成缺陷。建议改名 `interim_vs_final_pixels` 并注明「仅供诊断，不参与判据」，或者直接不再计算（见 E4）。

## 5. 对既有《代码评审报告.md》的更正

| 条目 | 旧结论 | 实测更正 |
| --- | --- | --- |
| E7 合并 | 「`garbage=4` 全量重建是 3456 页合并的时间与内存主因，建议换 qpdf」 | **不成立**。1476 页 / 17 MB 输入，`garbage=4` 用时 **0.13 s**、内存增量 <1 MB。改成 `garbage=0/1` 时间不变但产物 **17.01 MB vs 5.86 MB（2.9×）**，因为失去了对象去重。建议**保留 `garbage=4`**，不要引入 qpdf 依赖 |
| E9 少色图 | 「`quantize()` 是优化阶段的主要 CPU」 | 方向对、程度要收：占总 `optimize` 的 **28%**，而 PNG 往返与重复索引合计比它更值钱 |
| F10 抽样 | 「固定步长会系统性漏检」 | 已证实，并补一条：`pages[-1] = n-1` 的修补会让末页被重复采样两次（我改随机抽样后同一份 PDF 的对象数从 37 变 39，说明抽样口径本身不稳） |
| D4 体积 | 「numpy 来自 `PIL.ImageFilter.Color3DLUT`，可裁 35–50 MB」 | 数据核对无误：PYZ 里 numpy 1379.9 KB、PIL 571.7 KB；CArchive 里 `numpy.libs` 20.2 MB + `numpy` 6.1 MB 与 `PIL` 12.9 MB。但真正的体积大头是 **pymupdf 93.2 MB（不可裁）**，所以 `--exclude-module numpy` 省的是 26 MB 级，不是 50 MB 级 |

## 6. 功能侧建议（按价值排序，均与旧报告不冲突）

1. **取消与安全退出**：`threading.Event` 在「文档之间 / 阶段之间 / 每 200 张图」检查；主按钮在忙时变「取消」；关窗若 `STATE["busy"]` 弹确认。现在 `WM_DESTROY` 直接 `PostQuitMessage`，daemon 线程被强杀。
2. **中间 PDF 挪到 `%TEMP%`**：现在建在源目录（`unique_paths`，`pdf_tool.py:628`），中断即残留几百 MB，OneDrive 还会同步它。只有最终成品需要写回源目录。
3. **原子写**：`opt.optimize` 与 `merge_pdfs` 都直接写最终名。改 `out + ".part"` + `os.replace`，崩溃不再留下"名字完整、内容截断"的 PDF。
4. **落盘日志 + 批量 CSV 台账**：`%APPDATA%\WordToPdfTool\logs\`，批量结束输出「文件名/页数/导出体积/成品体积/一致数/差异数/无法比对/耗时/结果」。25 份跑一次 1336.8 s 的批量，现在回答"第 37 份为什么失败"只能翻屏。
5. **设置持久化**：`settings.json` 存转换通道、保留中间 PDF、自动合并、上次目录。
6. **拖放**：`DragAcceptFiles` + `WM_DROPFILES`，约 30 行，最自然的入口。
7. **`--version` 与版本资源**：exe 的 FileVersion/ProductVersion/Company 全空；`--version` 打印版本 + 依赖版本 + Python 版本，和 `--selftest` 组成验收闭环。
8. **`.doc` / `.wps` 支持**：先用 WPS COM 另存为临时 `.docx` 再走现有流程，能解掉 README §六「仅支持 .docx」这条硬限制。
9. **合并增强**：书签/大纲随页偏移（现在 `insert_pdf` 不带 TOC 处理，几百页合并后目录全丢）、分隔页、按文件名/页数排序。
10. **增量优化**：把「Word media 摘要 → 已产出流摘要」存旁车缓存（`.pdfimgcache.json`），同一文档二次处理可跳过全部编码，分钟级降到秒级。

## 7. 现成补丁

`hotfix/v13_fidelity.py` —— 不需要改 `optimize_pdf_images.py`（源码本来就不在工作区），在 `pdf_tool.py` 顶部加两行即可：

```python
import v13_fidelity
```

```
python v13_fidelity.py --check "成品.pdf" "源.docx" 20
```

## 8. 建议实施顺序

**第一批（半天，风险极低，立刻见效）**
